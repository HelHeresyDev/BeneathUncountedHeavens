# Task: Evaluate CurioMesh for Autonomous AI-Generated 3D Asset Cleanup

## Objective

I recently installed **CurioMesh 0.9.9** in **Blender 5.3 on Ubuntu Linux**.

CurioMesh is an automatic retopology and mesh-cleanup extension that I want to integrate into my local AI game-development pipeline.

Your task is to **independently investigate, operate, and evaluate CurioMesh** using the tools available to you.

I want to determine whether you can autonomously turn raw ComfyUI-generated 3D models into optimized, visually faithful assets suitable for Unreal Engine 5.8.4.

This is an experimental capability test. Do not assume CurioMesh works perfectly or that its operations can necessarily be automated.

## Environment

- Operating system: Ubuntu 26.04 LTS
- GPU: AMD Radeon RX 7900 XTX, 24 GB VRAM
- Blender: 5.3
- CurioMesh: 0.9.9
- Unreal Engine: 5.8.4
- Development agent: OpenCode with local Qwen
- Blender MCP is available.
- ComfyUI-3D-rocm produces GLB assets using TripoSG and Hunyuan3D-based workflows.

CurioMesh was manually tested in Blender 5.3. It successfully generated a retopology preview from a roughly 40,000-face mesh and identified areas needing repair.

Blender displayed a warning about a top-level module named `_curiomesh_turbo`, but basic interactive operations appeared functional.

## Phase 1 — Discover CurioMesh

Before attempting any cleanup:

1. Locate the installed CurioMesh extension and identify its directory.
2. Inspect its Python modules, registered Blender operators, settings, and automation interfaces.
3. Locate any bundled documentation, agent skills, command-line examples, or API references.
4. Determine whether CurioMesh can be operated through:
   - Blender Python (`bpy`)
   - Blender MCP
   - Headless Blender
   - Its own agent automation tools, if available
5. Identify whether the native acceleration module works despite the extension warning.
6. Determine which operations require an interactive Blender UI and which can run unattended.

Document the actual operators and parameters you discover. Do not invent API names.

Use read-only inspection initially. Do not modify CurioMesh's installed files or Blender's configuration.

## Phase 2 — Select a Test Asset

Search for an existing GLB model generated by my ComfyUI-3D pipeline.

Prefer a previously generated lantern asset if one is available.

If several candidates exist, choose one with:

- High polygon count
- Existing textures or materials
- Recognizable geometric details
- Potential mesh defects or unnecessary geometry

Record its path, polygon count, material information, UV maps, object count, and any detectable geometry problems.

Do not modify the original asset.

Create a separate testing workspace and save copies of all inputs and outputs there.

If no suitable asset exists, report that rather than generating unrelated assets or downloading random models.

## Phase 3 — Autonomous Retopology

Attempt to process the selected asset using CurioMesh without requiring manual Blender interaction.

Start with a conservative game-asset preset.

Test at least three configurations if supported:

- **High fidelity:** prioritize geometry preservation.
- **Balanced:** seek meaningful polygon reduction with minimal visual degradation.
- **Aggressive:** test how far the mesh can be simplified before important details are lost.

For each configuration:

1. Import the original model.
2. Run CurioMesh's retopology operation.
3. Inspect the resulting mesh statistics.
4. Identify problematic areas using CurioMesh's available diagnostics.
5. Attempt automated repair if the extension supports it.
6. Preserve or recreate materials and UVs where supported.
7. Save the resulting mesh as a separate Blender file.
8. Export a GLB if the result is valid.

If an operation requires interactive UI context, investigate whether it can be invoked safely through Blender Python or Blender MCP.

Do not monkey-patch the extension or disable Blender's security checks merely to get the operation running.

If headless processing is unsupported, determine whether graphical automation is feasible and explain the limitation.

## Phase 4 — Objective Quality Evaluation

Do not consider an operation successful merely because Blender reports that it completed.

Compare each processed model against the original.

Collect the following measurements where feasible:

- Triangle and polygon counts
- Percentage reduction
- Vertex counts
- Object and connected-component counts
- Non-manifold edges
- Degenerate faces
- UV preservation
- Material preservation
- Texture resolution and availability
- Bounding-box changes
- Surface deviation
- Silhouette similarity

Pay particular attention to thin structures, openings, sharp edges, and small decorative features.

If practical, render the original and optimized models from identical camera positions using the same lighting and material settings.

Produce comparison images from at least front, side, and three-quarter views.

Do not claim a quality measurement was performed unless you actually calculated it.

A reduction in polygon count is not automatically an improvement.

## Phase 5 — Test Automated Correction

If a generated candidate has detectable defects, try to improve it using CurioMesh's available features.

Investigate whether its bad-spot detection and repair workflow can be automated.

The interactive UI supports reviewing individual problematic areas, marking regions, and attempting localized repairs.

Determine whether those operations expose usable Python interfaces.

If so, attempt one controlled automated repair and compare before-and-after geometry.

If not, explain exactly where automation stops and whether a human must intervene.

Do not fabricate successful repairs or bypass the feature by substituting unrelated operations without clearly labeling the alternative.

## Phase 6 — Unreal Readiness

Evaluate whether the best optimized mesh is suitable for Unreal Engine.

Check:

- Export format compatibility
- Geometry integrity
- Material and texture preservation
- Scale and orientation
- UV suitability
- Whether the mesh would benefit from generated LODs
- Whether further cleanup would be necessary

If automated Unreal import and validation are safely available, perform an isolated test in an appropriate temporary location.

Do not alter gameplay Blueprints, existing character assets, levels, or production content in Beneath Uncounted Heavens.

If an Unreal import test cannot be performed safely, report that limitation.

## Operating Constraints

**Preserve my working environment.**

- Do not uninstall or upgrade Blender, CurioMesh, ComfyUI, ROCm, PyTorch, or Unreal Engine.
- Do not install additional dependencies without explaining why they are required.
- Do not overwrite original GLB, Blender, or game project files.
- Avoid loading additional large GPU models while Qwen is active.
- Prefer CPU processing and headless execution where possible.
- Avoid launching graphical Unreal unnecessarily.
- Do not perform broad filesystem modifications.
- Keep temporary files organized in the designated test workspace.
- Use the existing Blender MCP integration when it provides a reliable interface.

You may create test scripts, inspect code, run isolated experiments, and iterate on failures.

## Success Criteria

The experiment succeeds if you can demonstrate that you independently:

1. Discovered CurioMesh's actual automation interfaces.
2. Loaded a real ComfyUI-generated asset.
3. Produced at least one optimized mesh using CurioMesh.
4. Measured meaningful geometric differences.
5. Preserved important visual features and textures, or clearly documented why that failed.
6. Saved reproducible outputs and a useful test report.

**Most importantly, distinguish between functionality that you personally verified, functionality documented by the developer, and functionality you could not establish.**

Do not claim success simply because an API call completed.

Begin by inspecting the installed extension and identifying its real automation capabilities. Then perform the experiment, using the results to decide whether CurioMesh deserves a permanent place in our development pipeline.
